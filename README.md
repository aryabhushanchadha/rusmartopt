# RuSmartOpt Backend

Real backend for RuSmartOpt — production tracking, order management, secure customer-facing order tracking, and a self-service marketplace for manufacturing SMBs in Moscow. This replaces the earlier static-HTML prototype's fake login and in-memory data with real auth, a real database, and a real fix for the public-tracking security issue that prototype had.

**Explicitly still out of scope:** RFQ/bidding/auction mechanics (the buyer-side "Маркетплейс"/"Мои запросы" panels are still an honest "Скоро" demo). Seller subscription billing and buyer↔seller messaging **are now built** — see the section below. Plan history: `~/.claude/plans/structured-gliding-ullman.md`.

## Marketplace: self-service seller listings + real SEO

Sellers (existing `supplier`-type accounts) can now register and maintain their own product listings from the dashboard's "Мой каталог" panel — create, edit, publish/unpublish, delete, all self-service, no admin involvement. Publishing a listing (or saving a company profile) lazily assigns the company a public URL slug.

**The public marketplace is genuinely server-rendered**, not client-templated — `GET /postavshiki`, `/postavshiki/:companySlug`, `/postavshiki/:companySlug/:listingSlug` are real EJS-rendered HTML responses with unique `<title>`/`<meta description>`/canonical/Open Graph tags per page and JSON-LD (`schema.org/Product`, `Organization`, `BreadcrumbList`). This matters specifically because the target market is Russia, where Yandex has historically been weaker than Google at indexing JS-rendered SPA content — a plain client-templated marketplace page would have been much less likely to actually get indexed. `GET /sitemap.xml` and `GET /robots.txt` are generated from live published data only; unpublished/draft listings never appear on any public page, in the sitemap, or in search results, and 404 if guessed directly. EJS's auto-escaping (plus explicit `<` → `<` escaping inside the JSON-LD `<script>` blocks) is the XSS control here — this is the first surface in the app rendering seller-submitted free text into a public, unauthenticated page, verified with a dedicated XSS regression test (`tests/market-public.test.ts`).

Cyrillic titles/company names get transliterated into Latin URL slugs (`src/utils/slug.ts`, e.g. "Стеллаж торговый МГ-200" → `stellazh-torgovyy-mg-200`) — the standard practical RU→Latin scheme, matching how Yandex itself transliterates URLs. Listing slugs are unique per seller, not globally, so two sellers can each have a "Стеллаж торговый" listing without colliding.

**No fake "request sent" button.** RFQ/messaging-to-seller still isn't built, so listing pages show real seller info and an honest "coming soon" note instead of a CTA implying a message was sent when nothing happened server-side — the same overclaiming pattern already fixed once elsewhere in this app (see below), not reintroduced here.

**Images are a validated `https://` URL field, not file upload**, deliberately — this codebase has zero upload infrastructure (no multer, no static-serving, no MIME/size validation), and building that correctly is real scope on its own. Fast-follow path documented in the plan file: an `ImageStorage` interface (same seam as the existing `SmsProvider`) swappable from local disk to Yandex Object Storage, no schema change needed later.

One implementation note: JSON-LD construction was pulled out of the EJS templates into typed, unit-testable TypeScript (`src/modules/market/seo.ts`) rather than building it inline in the views — the plan sketched separate `jsonld-product.ejs`/`jsonld-organization.ejs` partials, but keeping schema-shape logic in `.ts` and using one generic `partials/jsonld.ejs` for safe serialization is more testable and was a better outcome than the original file split, so I deviated from the plan's exact file list here.

**Positioning: all manufacturing industries, by founder decision.** Earlier agent advice (Business Strategist, Deal Strategist) recommended narrowing to one vertical as a GTM beachhead. The founder explicitly chose to broaden instead — both the messaging (landing page, marketplace copy) and the actual product now reflect this: `Company.industry` is a free-text field (registration form offers a starting list — Мебель, Металлообработка, Упаковка, Текстиль, Пластик, Электроника, Пищевое производство, Другое — but doesn't restrict to it), so the "any industry" claim is backed by real capability, not just copy. The production-stage Kanban (`STAGES` in the frontend) is still a fixed, furniture/metal-oriented list (Раскрой, Сборка, Покраска, ОТК, Упаковка) — a genuinely universal product would eventually need per-company configurable stages, which is not built yet.

## Payments (ЮKassa) + buyer↔seller messaging

**Billing.** Sellers subscribe to one of two real plans (`software` 10 000 ₽/мес, `marketplace_full` 24 999 ₽/мес, with a promo price of 15 000 ₽/мес for the first `PROMO_SLOTS` — default 100 — marketplace subscribers) from the dashboard's "Подписка" view. Checkout creates a real ЮKassa payment and redirects to their hosted checkout page.

**The payment-confirmation security model is the important part here.** ЮKassa webhooks carry no HMAC signature, so `POST /api/billing/webhook/yookassa` never trusts the webhook body: it (1) rejects deliveries from outside ЮKassa's published IP ranges (`YOOKASSA_WEBHOOK_IP_ALLOWLIST`, cheap first-pass filter, not the real boundary), (2) records `(providerPaymentId, eventType)` in a uniquely-constrained ledger table so a retried/duplicate delivery is a no-op before anything mutates, then (3) — the actual authentication — re-fetches the payment by id from ЮKassa using our own secret-key credentials, and only that re-fetched status ever flips `Payment`/`Subscription` state. A forged POST to the webhook endpoint cannot forge what our own authenticated GET returns. Covered by `tests/billing-webhook.test.ts` (untrusted IP, duplicate delivery, unknown payment id, and — the important negative case — a webhook body that *claims* success while the re-fetched status is still pending does **not** activate anything).

**Paywall enforcement is off by default.** `PAYWALL_ENFORCEMENT_ENABLED=false` means publishing a listing is never blocked by subscription status, on purpose — the founder's own "be the first seller" plan and early pilot sellers shouldn't get locked out while the product is unproven. The gate exists (`listingsService.setPublished`, `tests/paywall-flag.test.ts`) and is a one-line env flip when you're ready to actually charge for marketplace publishing; flipping it never retroactively unpublishes already-live listings.

**Renewals** are handled by `npm run charge-renewals` (`scripts/chargeRenewals.ts` → `src/modules/billing/renewalService.ts`), which is **not** scheduled automatically — wire it to a daily cron / Yandex Cloud Function trigger yourself. It charges the saved payment method for subscriptions past their period end, marks a subscription `past_due` if the charge fails or there's no saved method, and `expired` after `PAST_DUE_GRACE_DAYS` (default 7) of unresolved `past_due`. **Recurring/automatic charges against a saved method require ЮKassa's merchant-level approval for rebilling** — a real account-side step you'll need to request once you have a live merchant account, not something built in code.

**Messaging.** A buyer clicks "Написать поставщику →" on any real public listing page (`src/views/market/listing.ejs`) and lands in a real conversation thread, scoped one-per-`(listing, buyer company)` so re-contacting continues the same thread. Since the public listing pages and the authenticated SPA are different origins, an unauthenticated buyer's intent survives login/register via a `?compose_listing=...` query param handed off through `sessionStorage` (`frontend/index.html`, `captureComposeIntent`/`handleComposeIntent`) — they land straight back in the compose box after signing in. New messages trigger the existing Telegram/SMS `NotificationService`, reusing real infrastructure rather than adding a new channel. Tenant isolation follows this codebase's standing convention exactly: a company uninvolved in a conversation gets 404, never 403 (`tests/messaging.test.ts`).

**Not done:** no UI to link a company-level Telegram chat yet (`Company` has `notifyPhone`/`notifyChannel`, editable via `PATCH /api/companies/me`, but nothing prompts a seller to set it up) — SMS is the functional notification path today. No card-update UI for a `past_due` subscription; the workaround is re-running checkout, which creates a fresh payment against the same subscription. **The new billing/messaging frontend views (`Подписка`, `Сообщения` in both apps, the listing-page CTA) were built and manually verified against the running API via `curl`, but not clicked through in an actual browser** — Chrome browser tools weren't enabled in the session that built them. Click through both flows yourself before trusting them fully (see the "Мой каталог" note further down for the same caveat pattern).

### Concurrency fixes (double-charge prevention)

A Payments & Billing Engineer review of the first version of this billing code found real double-charge races, not just theoretical ones — fixed and regression-tested in `tests/billing-concurrency.test.ts`:

- **Checkout and renewal idempotency keys were random per call**, defeating ЮKassa's own idempotency-key deduplication — two overlapping renewal-job runs, or a double-clicked "Оформить подписку", could each open a genuinely separate ЮKassa charge. Both now derive a **deterministic** key (`checkout:{subscriptionId}:{attemptNumber}`, `renewal:{subscriptionId}:{currentPeriodEnd}`), so a concurrent duplicate reaches ЮKassa with the *same* key — ЮKassa returns the same payment object for both, and this app's own `Payment.providerPaymentId` unique constraint catches the second local insert as a no-op rather than a second charge. A checkout attempt that later resolves to canceled still gets a fresh key on retry, so this doesn't block a genuine second purchase attempt.
- **The webhook's `payment.status !== "pending"` check was read-then-act, not atomic** — two different ЮKassa event types for the same payment could both pass it before either had written anything, double-firing `activatePayment` (and its notification). `activatePayment`/`markPaymentCanceled` (`service.ts`) now use a conditional `updateMany({..., status: "pending"})` as the actual claim; only the call whose update affects a row proceeds. The status check in `webhookService.ts` is now documented as a cheap fast-path, not the guard.
- **The promo-slot count-then-create was a classic write-skew race** — concurrent signups near the last discounted slot could all read "still available" and over-issue the discount. `ensureSubscription` now runs the read+create under Postgres `SERIALIZABLE` isolation, with a short retry-with-jitter loop on the resulting `P2034` conflict, so the promo count is provably never exceeded even under concurrent load.
- **Messaging had no rate limiting** — `sendMessage`/`startConversation` each fire a real SMS/Telegram send, making unlimited posting a paid-API abuse vector, not just spam. Added `userRateLimit` (`src/middleware/rateLimit.ts`, scoped per-account rather than per-IP) at 20 new conversations/hour and 60 messages/hour per account.

Not fixed, and deliberately out of scope for this pass: no dunning/retry schedule during the `past_due` grace window (only expiry), and the re-fetched payment amount from ЮKassa isn't cross-checked against the expected amount before activation. Both were rated low-severity by the review.

## Public marketplace JSON API (`/api/market/*`) — for the upcoming mobile app

Until now, browsing other sellers' listings only existed as server-rendered EJS pages at `/postavshiki/*` (real HTML, built for SEO — see the marketplace section below) with no JSON equivalent. A React Native mobile app has no concept of a "public webpage" to browse, so `src/modules/market/publicApiRoutes.ts` adds a thin, read-only JSON layer over the exact same service-layer queries the EJS pages already use (`listPublishedListings`, `getPublicCompanyProfile`, `getPublicListing` in `src/modules/market/service.ts`) — no query logic duplicated, so the two surfaces can't silently diverge (e.g. one leaking a draft the other correctly hides).

- `GET /api/market` — paginated catalog (`{items, total, page, pageSize, totalPages}`), same 24-per-page as the HTML catalog.
- `GET /api/market/companies/:companySlug` — company profile + its published listings; 404 for a nonexistent slug *or* a company with zero published listings (the same thin-content rule the HTML route already enforces).
- `GET /api/market/companies/:companySlug/listings/:listingSlug` — single listing + its company.

Mounted in `src/app.ts` right next to `/api/track`, unauthenticated and outside the CSRF chain — these are read-only GETs with nothing to protect. `tests/market-api.test.ts` (10 tests) mirrors `tests/market-public.test.ts`'s exact scenarios (published/unpublished/nonexistent, thin-content 404, pagination boundaries, garbage page numbers) against the JSON responses instead of scraping HTML — confirmed passing against the real seeded dev database via `curl`, not just the test suite.

**Not built here, and deliberately out of scope for this endpoint**: the "Написать поставщику" (message this seller) action from a mobile listing screen needs a deep-link-based version of the web app's query-param + `sessionStorage` compose-intent handoff — that's mobile-app-side work, tracked in the separate mobile app plan, not a backend change beyond what's already shipped.

## Cross-role review: seller, buyer, admin (fixes applied)

Ran a dedicated code-level audit of all three user journeys end to end (not a browser click-through — Chrome tooling isn't available in this environment, disclosed consistently throughout this log). Real, concrete issues found and fixed:

- **Admin dashboard timezone bug.** The 30-day growth chart and "today" bucketing used UTC midnight instead of Moscow local time — a signup or payment between 00:00–03:00 Moscow time landed in the wrong day's bucket. Russia has used a single fixed UTC+3 offset (no DST) since 2014, so `src/modules/admin/service.ts` now buckets against Moscow-local day boundaries directly, with a regression test (`tests/admin.test.ts`) that plants a company at 01:30 Moscow time (22:30 UTC the day before) and asserts it lands in the correct day.
- **Four remaining untranslated toasts**, found by grep after the language-support phase claimed full toast coverage: the seller's ship-order flow, the buyer's pre-login "log in to message the supplier" prompt, the supplier's own order-search-not-found toast, and (see below) the wrong-role compose message. All now route through `t()`.
- **Buyer compose-intent dead end.** Clicking "Написать поставщику →" while already logged in under the *wrong* role (e.g. a stale supplier session on a shared device) used to permanently discard the intent to message that seller with no recovery path. It's no longer cleared in that case — logging out and back in as a buyer resumes it — and the toast now says so explicitly instead of just "log in as a buyer" (misleading when already logged in).
- **Admin login form leaked raw JSON** on a malformed submission or once rate-limited — only the wrong-password case got a properly rendered error page. Rate limiting is now inlined in the route itself (not the shared JSON-only `ipRateLimit` middleware) so every failure mode re-renders the actual login page.
- **Company profile fields couldn't be cleared** once set — the PATCH schema and service only supported "provide a value" or "omit the key" (leave unchanged), with no way to explicitly unset a website/logo/phone/etc. `updateCompanySchema` fields are now `.nullable()` (the underlying DB columns already were), and the frontend sends `null` for a blanked field instead of silently omitting it.
- **Silent SMS delivery failure** — a seller who selects the SMS notification channel but leaves the phone blank got zero feedback anywhere. The profile view now shows an inline warning in that state.

**Update: 125/125 passing.** New coverage: `tests/orders-shipping.test.ts` (10 tests) — the shipping/production endpoints (`ship`, `ship-stage`, `notify`, `log`, `notifications`) had **zero** test coverage before this pass despite being a core part of the seller journey, breaking this project's own real-Postgres testing discipline; two new marketplace pagination tests in `tests/market-public.test.ts`; two new admin tests for the JSON-leak fix; one new companies test for field-clearing; one new admin test for the timezone edge case.

**Update (mobile API): 135/135.** `tests/market-api.test.ts` (10 tests) added for the new `/api/market/*` JSON endpoints — see above.

**Not fixed, disclosed rather than silently left:** backend `HttpError` messages (validation errors, "order not found," etc.) are still Russian-only regardless of `User.language` — translating those touches every error call site across every module, real separately-scoped work. A demoted/deleted admin's cached session role isn't re-validated against the DB until natural expiry (sliding TTL) — consistent with the admin dashboard's already-disclosed "no audit log, no 2FA" limitation.

## Multi-language support (Russian / English / Chinese / Vietnamese)

Scope, by explicit founder decision: the **authenticated dashboard** (both apps, plus the login/register screen and the landing page's nav/hero) — not the public marketplace SEO pages (`/postavshiki/*`), which are a separate surface with their own real-SEO constraints (see the marketplace section above) and stay Russian-only for now. Two independent language settings, matching how this data is actually shaped:

- **`User.language`** — interface language, chosen per person (a language switcher — `RU`/`EN`/`中文`/`VI` — sits in both topbars, the login screen, and the landing nav). Persisted server-side via `PATCH /api/auth/language` and returned on every `/api/auth/me`, with `localStorage` as the pre-login/offline fallback. Switching re-renders the currently visible app immediately — no reload.
- **`Company.notifyLanguage`** — the language of SMS/Telegram *notifications* sent to that company's configured phone/channel (order stage changes, billing events, new messages). Company-level, not user-level, because a notification is addressed to whoever answers that phone/chat, not to a specific logged-in session. Editable from "Профиль компании" alongside `notifyPhone`/`notifyChannel`. Real message templates exist for all four languages in `src/i18n/notifications.ts` (order status, shipped, billing activated/canceled/past-due/expired, new message) — verified with a dedicated test (`tests/notification-i18n.test.ts`) that checks actual message *content* per language, not just that a language field exists somewhere.

**What's translated in the dashboard**: all navigation, page headers, table columns, status labels, form fields and buttons, the listing-creation drawer, the order-detail drawer, the new-order form, messaging, billing, the company profile, toast notifications, and number/date formatting (`toLocaleString`/`toLocaleDateString` now follow the active language's locale, not a hardcoded `ru-RU`). 310 keys × 4 languages, cross-checked by script for missing/orphaned keys before every commit that touches them (zero found).

**What's deliberately NOT translated, and why**: the demo-only content that predates real backend support for those features — the RFQ list, auction lots, and "Мои запросы" deal history are all fictional placeholder data (no RFQ/bidding backend exists yet, already marked "Скоро"/"Coming soon" elsewhere in this codebase) — translating fictional company names and deal amounts has no real value, so only their surrounding chrome (headers, buttons) is translated. The landing page's long-form marketing paragraphs (feature card descriptions, pricing tier copy) are also still Russian-only — only its nav, hero, and CTAs were translated, since a full marketing-copy translation pass is a copywriting task more than an engineering one. **Backend error messages returned to the client** (validation errors, "order not found," etc.) are still Russian-only everywhere — translating those would mean touching every `HttpError` call site across every module, which is real, separately-scoped work, not something folded into this pass silently.

## Seller profile + free product listing

The dashboard's "Профиль компании" view (new nav item, supplier only) is a real, complete company-profile editor — industry, city, INN, description, website, logo URL, and notification phone/channel, all wired to `PATCH /api/companies/me`. Previously `industry`/`city`/`inn` could only ever be set once, at registration — a seller who mistyped their industry or moved cities had no way to fix it; `updateCompanySchema`/`updateOwnCompany` now accept all three. `name` is deliberately still not editable: it seeds the public URL slug on first save (`ensureSlug`), and slugs are immutable once assigned so a shared link never breaks.

Both the profile view and the existing "Товар" listing-creation drawer now say explicitly that listing products is free — matching reality: `PAYWALL_ENFORCEMENT_ENABLED` defaults to `false` (see the payments section above), so publishing costs nothing unless that flag is deliberately turned on later. If it ever is, this copy will need a matching update — it's an honest statement of current behavior, not a permanent promise baked into the UI.

`tests/companies.test.ts` (7 tests) covers the full profile round-trip: reading the registered profile, editing the newly-unlocked fields, the pre-existing fields together, HTTPS-only URL validation, and that a profile save lazily assigns the public slug.

## Admin metrics dashboard

`GET /admin` — a real, server-rendered (EJS) dashboard showing platform growth and day-to-day activity: total suppliers/buyers, a 30-day daily-signups chart (supplier vs. buyer, zero-filled so a real gap in signups shows as a real zero, not a missing bar), a seller funnel (registered → added a listing → published a listing → active subscription), industry breakdown, billing (subscriptions by status/plan, promo-slot uptake, total revenue from *succeeded* payments only, payments today), marketplace activity (listings, conversations, messages today/this week), and a live feed of the 20 most recent company signups. All numbers are computed live from Postgres on every request (`src/modules/admin/service.ts`) — nothing cached or precomputed.

**Access**: no self-registration path exists for the `admin` role (`registerSchema` only allows `supplier`/`buyer`) — admin accounts are created directly in the DB, same as `scripts/seed.ts` does (`admin@rusmartopt.ru` / `password123` in the seeded dev DB — **change or remove this before any real deployment**, it's a demo credential). `GET /admin/login` is a plain HTML form (not the SPA) since this is a page a human navigates to, not a fetch()-driven API call — an unauthenticated visitor is redirected there (302), not shown raw JSON; a logged-in non-admin gets a plain 403 page, not a login loop. This is the first authenticated, browser-rendered page in the app, so `express.urlencoded()` body parsing was added alongside the existing `express.json()` — only this form needs it.

Not built: any way to promote a user to admin from within the app, write actions from the dashboard (it's read-only), auth beyond a role check (no 2FA, no audit log of who viewed it), and no UI affordance anywhere in the SPA linking to `/admin` — reach it by URL. `tests/admin.test.ts` covers the access-control gate (redirect/403/200 cases) and the metrics math itself (funnel counts, revenue only from succeeded payments, day-bucketing) against real seeded data, not just the rendered HTML.

## Local setup

```bash
cd ~/projects/rusmartopt-backend
cp .env.example .env          # already done once during the build; edit as needed
npm install
docker compose up -d postgres redis   # start just the DB + cache locally, not the api yet
npx prisma migrate dev --name init    # creates the database schema
npm run seed                          # demo data: 2 suppliers, 1 buyer, 5 orders
npm run dev                           # starts everything — API, SPA, marketplace, admin — on :3000
```

That's it — **one process, one port.** `frontend/index.html` and `frontend/api.js` are now served directly by this same Express app (see "Domain" below for why), so the old two-terminal setup (a separate `npx serve -l 5173` for the frontend) is gone. Open `http://localhost:3000`. Demo logins from the seed script: `anna@zavod.ru` / `password123` (supplier, has an active promo-priced `marketplace_full` subscription and one demo conversation seeded), `igor@stroydvor.ru` / `password123` (buyer), `admin@rusmartopt.ru` / `password123` (admin — go to `http://localhost:3000/admin/login`, not the SPA; see "Admin metrics dashboard" above).

`YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` are empty by default — checkout will fail loudly with "ЮKassa не настроена" until you create a real ЮKassa **test-mode** merchant account and set both. Everything else (subscription status, payment history, messaging) works without them, since the seed script creates a subscription directly.

## Domain

The production domain is **`rusmartopt.ru`** (purchased via reg.ru). Everything that needs a real public URL — `PUBLIC_BASE_URL`, canonical/OG tags, `sitemap.xml`, and the SMS/Telegram tracking links — now reads from one env var (`PUBLIC_BASE_URL`, see `.env.example`) instead of being hardcoded, so pointing the whole app at the domain is a one-line config change once hosting exists.

**Apex (`rusmartopt.ru`), not `www.`, is the canonical form** — one judgment call worth flagging explicitly since it was purchased as `www.rusmartopt.ru`: the mobile app (`rusmartopt-mobile/app.json`) already hardcodes apex for its universal-link config (`applinks:rusmartopt.ru`, `android.intentFilters` on `https://rusmartopt.ru/app/*`), and apex is the more standard canonical choice for a site that's also an app deep-link target. **`www.rusmartopt.ru` should redirect to apex**, not serve a separate copy of the site — reg.ru's DNS panel can do this with a simple redirect/forwarding record, or it can be handled at the reverse proxy once one exists. If you'd rather make `www.` the canonical form instead, say so — it's a small, mechanical change (env var + the mobile app's two domain-association files) as long as it happens before real users/backlinks accumulate.

**Single-origin serving is already in place**, which is what makes a one-domain deploy simple: `frontend/index.html`/`frontend/api.js` (the SPA), the EJS marketplace pages, the admin dashboard, and the JSON API are all served by the same Express process on one port (see "Local setup" above) — no separate frontend host, no cross-origin cookie concerns, one TLS cert covers everything.

**What's still needed before `rusmartopt.ru` actually resolves to this app** (all downstream of standing up Yandex Cloud hosting, not yet done — see below): an A/AAAA record pointing apex at the server's public IP, a `www` redirect record, a TLS cert (Let's Encrypt via the reverse proxy, or Yandex Cloud's own cert management), and setting `PUBLIC_BASE_URL=https://rusmartopt.ru` + `NODE_ENV=production` (which flips the session cookie's `secure` flag on) in the production `.env`. The exact DNS record values (target IP) can only be given once a Yandex Cloud VM/load balancer actually exists.

## Deploying to rusmartopt.ru

`docker-compose.prod.yml` + `Caddyfile` are ready to run once you have a server — they add a Caddy reverse proxy (automatic Let's Encrypt TLS for both `rusmartopt.ru` and `www.rusmartopt.ru`, the latter just redirecting to apex — see "Domain" above) in front of the same `postgres`/`redis`/`api` setup as local dev, with the database/cache no longer exposed on public host ports.

1. **Get a VM.** Yandex Cloud Console → Compute Cloud → Create VM: Ubuntu 22.04, 2 vCPU / 4 GB RAM is enough to start, region `ru-central1` (152-ФЗ — keeps customer data in Russia), attach a **static public IP**. In the security group, open 22 (SSH — restrict to your own IP if you can), 80, and 443 only; nothing else needs to be public.
2. **Get the code onto the server.** This repo has no git remote yet — push it to a private GitHub repo first (`git remote add origin <url> && git push -u origin main`), then on the VM: install Docker (`curl -fsSL https://get.docker.com | sh`), `git clone` the repo.
3. **DNS at reg.ru.** In reg.ru's DNS management for the domain, add two **A records** pointing at the VM's static IP: one for `@` (apex) and one for `www`. Don't use reg.ru's own domain-forwarding feature for `www` — Caddy handles that redirect itself, and needs `www` to actually resolve to the server so it can also issue a cert for it.
4. **Production `.env`** on the server: `cp .env.example .env`, then fill in real values — `PUBLIC_BASE_URL=https://rusmartopt.ru`, `NODE_ENV=production`, a strong `POSTGRES_PASSWORD` (and match it into `DATABASE_URL`, with host `postgres` not `localhost`: `postgresql://rusmartopt:<same password>@postgres:5432/rusmartopt?schema=public`), plus the real ЮKassa/SMSC/Telegram credentials once you have them. Never commit this file.
5. **Bring it up:**
   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   docker compose -f docker-compose.prod.yml exec api npx prisma migrate deploy
   ```
   (Deliberately not `npm run seed` — that's demo data for local dev, not for a real production database.)
6. **Verify:** `https://rusmartopt.ru` loads the SPA over a valid cert, `https://www.rusmartopt.ru` redirects to it, register/login works, and an order's tracking-link SMS/Telegram message resolves correctly (see the "Domain" section above for why that link was previously dead).

Not yet done, worth doing before this carries real customer traffic: switching from the self-hosted `postgres` container to Yandex Managed PostgreSQL (automatic backups, no single-VM data-loss risk), a deploy script/CI step instead of manual `git pull && docker compose up -d --build` on the server, and enabling `RATE_LIMIT`/CORS hardening appropriate for a public production origin (see "Known follow-up work" below).

## What's real vs. what still needs Yandex Cloud

Everything in this repo runs locally via Docker. **Nothing has been deployed to Yandex Cloud** — that's explicitly a separate, later phase (provisioning Managed PostgreSQL, pushing the container image, DNS, TLS). Don't treat this repo as production-ready until that phase happens and the verification checklist in the plan file has been run end-to-end.
